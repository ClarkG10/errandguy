# ErrandGuy — Startup MVP Audit: Dead Code, Duplication & Launch Readiness (2026-09-06)

*Seven specialist auditors across API dead-code, mobile dead-code, database, duplication, overengineering, critical-workflow failure points, and performance/UX. **Every claim was adversarially re-verified** by a second agent instructed to refute it — in particular, no "unused" verdict was accepted without independent greps of BOTH repos (mobile calls API routes by URL string; expo-router routes by file path; Filament and `routes/console.php` reference classes dynamically). 60 findings survived verification: **1 P0, 9 P1, 24 P2, 26 P3**.*

*The P0 and the three highest-value P1s are **implemented, tested, and committed** (§9). Suites: 993 API tests, 815 Jest tests, `tsc` clean.*

---

## 1. What the system actually does

A two-sided on-demand errand/delivery marketplace for the Philippines, pre-launch.

- **Customers** post errands (delivery, purchase-and-deliver/shopping, bill payment, queueing, transportation), pay by wallet / GCash / Maya / card / cash, watch the runner live, chat, then rate and tip.
- **Runners** pass KYC, go online, receive and accept offers, navigate, capture proof (photo / PIN / signature), complete, and withdraw earnings.
- **Operators** work a Filament v4 admin: moderate users and bookings, verify runner KYC, process payouts, handle support tickets and disputes.
- **Money** runs through Xendit plus an internal wallet with an append-only `wallet_transactions` ledger; commission is `total − payout`; cash (COD) settles at completion.

**Scale:** 51 API controllers, 15 services, 29 models, 16 commands, 124 Filament files, 38 DB tables; 74 mobile screens, 106 components, 25 hooks.

## 2. The core business workflows

1. **Book → pay → match → track → complete → receipt** (customer). This is the revenue path; everything else is support.
2. **Go online → offer → accept → proof → complete → earnings → payout** (runner). This is the supply path; if runners aren't paid reliably and promptly, supply evaporates.
3. **Verify runners → process payouts → resolve complaints** (ops). Small but load-bearing: it is the only place a human can correct money.

Everything else — heatmap, referrals, promos, trip-share, multi-stop, scheduling — is an accelerant, not the business.

## 3. Headline: the system is not over-featured, it is over-*duplicated*

The single most useful conclusion from this audit. The feature set is broadly appropriate for a marketplace MVP, and the machinery that looks fanciest (SOS fan-out, offline mutation queue, idempotency middleware, the payment state machine) is **correctly sized and must not be cut** — it is what makes a stranger-to-stranger marketplace safe and its money trustworthy.

What is genuinely wrong is that **the same job is done twice in several places**, which for a small team means two things to maintain and two places to drift apart. Three of these have *already* drifted, and one of them can never work at all.

## 4. Critical bugs & failure points (the launch blockers)

**🔴 P0 — The pull-reconciler killed the charge but not the booking. `FIXED`**
An online booking is matched — and can be accepted and completed — *before* its charge is captured. The webhook had a teardown for an abandoned checkout; the reconciler did not. And the reconciler is the path that usually **wins**: the app polls status every 3s from the moment checkout opens, so it terminalizes the charge first, which then permanently disarms the webhook (`canAdvance=false` ⇒ its teardown never runs). The most common abandonment in the product — open GCash, change your mind, decline — therefore left the booking fully live. The runner drove out, did the errand, was credited **₱0**, and neither party was told the booking was void.

**🟠 P1 — Booking charges had no scheduled reconciler. `FIXED`** The primary revenue path was the only money-in flow with no safety net (top-ups and payouts each had one). The customer's poll isn't durable, so a dropped webhook leaked both ways: a genuinely paid booking left `pending` credits the runner nothing at completion, and an abandoned one stays live — invisible to the auto-cancel job and stranded reaper, which only look at `pending`/`no_runner`.

**🟠 P1 — Gateway tips had no reconciliation on *any* path. `FIXED`** One dropped webhook and the customer's tip was captured at the gateway while the runner was never credited, with no recovery, automated or manual.

**🟠 P1 — A runner who accepts an errand has no exit.** No cancel endpoint, and they cannot even go offline. Anything that goes wrong mid-errand requires a human. *Open — needs a product decision on cancellation policy/penalty.*

**🟠 P1 — SOS fan-out is the last safety path still riding the queue worker.** Every other money/safety backstop was deliberately moved to run in the scheduler so it survives a worker outage. SOS wasn't. *Open.*

**🟡 P2 — Wallet debit and the booking's paid flag are not in one transaction.** A crash in that window takes the customer's money with no recovery. *Open — highest-value remaining P2.*

**🟡 P2 — A booking stranded at `delivered` is invisible to every backstop** and the runner is never paid. *Open.*

## 6. Dead & unreachable code (verified unreferenced)

**The big one — 🟡 P2: the entire Disputes subsystem can never receive a row.** ~970 lines (Filament resource, admin controller, dashboard counter, a 4-hour SLA pager) are fed by exactly one route — the legacy `POST /support/report` closure — whose only mobile caller has **zero references**. Real complaints land in the parallel Support Tickets system. Worse: **the only admin "Resolve + refund" tool lives behind this dead queue**, so the primary customer-refund workflow is unreachable in production. *Either wire the intake or delete the subsystem and move the refund action — but it cannot stay as-is.*

**Security-relevant — 🟡 P2:** `/api/v1/admin/*` is client-less, yet `/api/v1/admin/login` still mints an **8-hour privileged bearer token on the public internet**. Removing it deletes a whole second admin credential surface.

Also verified dead and safe to delete: `RouteDeviationAlert` (a safety event never dispatched), `LocationService::getNearbyRunners`/`getRunnerLocation`, `RunnerErrandPolicy` + `RunnerProfilePolicy` (never invoked), `BookingPaymentStatus` enum (zero references), `ShoppingListController` + its route, `GET /payments/{id}/receipt/pdf`, a Postgres-only migration that is a permanent no-op on MySQL, the vite/tailwind build toolchain that only builds the stock Laravel welcome page; and in mobile: the abandoned `zod` validation stack (129 dead lines + an orphan runtime dep, while all three auth forms still hand-roll the rules it was built to replace), 539 lines of orphaned hand-drawn SVG, `OnDemandMap`, `hooks/useBooking.ts`, root `App.tsx`/`index.ts` Expo-template leftovers, and **two unused native map SDKs autolinked into every build**.

## 7. Simplify / Defer (MVP triage)

- **DEFER: Transportation (ride-hailing).** It is a separately regulated business threaded through the errand codebase, and it is **one admin toggle** to keep out of the launch catalog. Narrowing the 10-type catalog also sharpens the product story.
- **DEFER: the 843-line speculative mobile preload layer** — complexity buying little at pre-launch traffic.
- **SIMPLIFY: the 3 god screens** (3.3–3.5k lines, ~30 `useState` each) re-render wholesale on every GPS tick. The only structural render cost worth acting on.
- **KEEP (do not cut, despite looking like extras):** SOS + trusted contacts, the offline mutation queue, idempotency, the payment state machine, KYC. These are what make the marketplace safe and the money trustworthy.

## 8. Database

Genuinely strong for an MVP: **every money column is `decimal`** (zero floats across 76 migrations), UUID PKs are consistent, and hot-path indexes are purpose-built. Real issues: `dispute_tickets` has no reachable writer (§6); **`bookings.payment_status` is a money-deciding column raw-`update()`d from 19 sites** with no drift detector; the **DB-level money UNIQUE guards can silently skip themselves at deploy** with nothing verifying they exist in prod; 8 provably-redundant indexes on the busiest tables; and `runner_locations` keeps 24h of GPS history when all 3 readers only ever fetch the single latest row per booking.

## 9. What was implemented this pass

Committed in `284e707` (money) and `3793da8` (mobile) — 993 API tests, 815 Jest, `tsc` clean.

1. **P0 — reconciler teardown.** `cancelUnpaidBooking` moved into `BookingSettlementService` and called from **both** settlement paths, exactly as `settlePaidBooking` already is. + 4 tests.
2. **P1 — `errandguy:reconcile-booking-payments`**, scheduled every 15 min beside its top-up and payout siblings, reusing the same reconcile path — plus a **detective sweep** that raises a critical alert for any errand delivered with no settled payment (the end state every leak in this family produces, which nothing else looked for). + 5 tests.
3. **P1 — gateway tip reconciliation** on both the read path and the sweep. + 4 tests.
4. **Bonus (found by our own test):** a terminal `FAILED`/`EXPIRED` no longer **downgrades a booking that is already paid** — a first attempt failing after a second succeeded would otherwise mark a paid errand unpaid and, combined with (1), cancel it.
5. **P1 — uploads downscaled.** Item photos (5 raw frames = 10–20MB against a 5MB/file cap, where one oversized photo 422s the whole batch and is never retried) and KYC (the highest drop-off point in runner activation) now use the `compressProofImage` helper the app already shipped but had wired into only 2 of 6 paths. Also corrected failure copy that told customers to do something impossible.

## 10. Prioritized roadmap

**🔴 P0 — done.** The free-errand money loss is closed on both settlement paths.

**🟠 P1 — before launch (6 open)**
1. Extract **one wallet credit/debit primitive**; route all 15 sites (and both runner-earning implementations) through it. This is the single highest-leverage maintainability fix — it retires the whole class of drift.
2. Route `RunnerPayoutController` through `WalletService::payout`.
3. **Delete the clientless admin REST API** — removes ~709 lines, ~650 lines of tests, a duplicated authorization matrix, and a public admin credential surface.
4. Give a runner **an exit** from an accepted errand (needs a policy decision).
5. Move **SOS fan-out** off the queue worker into the scheduler, like every other safety backstop.
6. De-duplicate the **chat screen** (and then the notification inbox).

**🟡 P2 — soon**
Resolve the **Disputes** subsystem (wire the intake or delete it and relocate the refund action — the refund workflow is currently unreachable); put wallet-debit + booking-paid-flag in **one transaction**; add a backstop for bookings stranded at `delivered`; add a **prod assertion that the money UNIQUE guards exist**; drop the 8 redundant indexes and the 2 unused native map SDKs; unify the runner working-radius meaning.

**🔵 P3 — later**
The remaining dead-code deletions, dark-mode palette, `runner_locations` retention, tracking-screen SWR migration, god-screen decomposition.

---

## Bottom line

For a pre-launch startup this codebase is in better shape than most: the money is genuinely well-protected, the schema is sound, and the safety machinery is correctly sized. The work that matters now is **subtraction, not addition** — delete the duplicated ops surfaces, collapse the copy-pasted ledger writes into one primitive, and resolve the two subsystems (Disputes, the admin REST API) that exist twice or not at all. The one thing that was actively costing money on every abandoned checkout is fixed.
