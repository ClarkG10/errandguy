## 1. Executive Summary

> **Consolidated verdict:** Sweep-2 does not change the decision — ErrandGuy remains NOT launch-ready — but it moves the bar further away, not closer. It opens two things sweep-1 missed: an entire Philippine Data Privacy Act compliance dimension full of pre-launch legal blockers (no real erasure, no persisted consent, a self-labeled "placeholder" privacy notice — dimension scored 42), and a new silent runner-money-loss path at the payout-reversal seam (MONEYX-1) plus a cross-account PII push leak (RT-1). It simultaneously confirmed the money core sweep-1 praised is genuinely sound and deeply tested, and undercut several worst-case fears (phone-OTP is not a hard signup gate, the Postgres-index-on-MySQL concern is already handled, NestJS dual-engine drift is unverifiable in this tree).

ErrandGuy has genuinely strong bones: the wallet/payment core, booking concurrency, IDOR/authorization posture, and mobile UX are above the bar for a marketplace at this stage, and a prior money-safety hardening pass verifiably closed the historic P0s (double-refund, payout double-debit, referral farming, cash-completion leak). It is not, however, safe to launch as-is. Three unresolved criticals gate it: runner KYC documents (government IDs, selfies, licenses) are served from a world-readable disk that any past customer can brute-force by the runner UUID they already know (SEC-1); production runs APP_DEBUG=true, leaking stack traces and internals on the admin panel and on every 5xx API response (DEVOPS-1); and there is no database backup, PITR, or disaster-recovery plan for the wallet/payments data (DEVOPS-2) — a single bad migration or disk failure is irreversible. Layered on top, roughly twenty high findings include real money-loss paths at the completion/settlement seam (runners never paid when a charge settles late, cash+promo bookings shortchanging the runner, cancel-charges-the-customer-with-no-refund, and a free-errand revival via retry-match), a money-moving admin panel with no 2FA and an editable free-text payout destination that lets an insider redirect a runner's funds, and a queue/scheduler single point of failure that silently freezes refunds, auto-cancel, and safety monitoring with zero alerting. Operational readiness is the systemic weakness — DevOps scored 44 — with no error tracking, no mobile crash reporting, only a trivial /up health check, in-place deploys with no rollback, CI running on SQLite against a MySQL prod, and a production mobile build shipping a placeholder Reverb key and the wrong API host. The verdict is a clear no-go until the three criticals plus the money-loss and insider-risk highs are closed and a minimum ops baseline (automated backups with a restore drill, error/crash tracking, a deep health endpoint with queue/scheduler alerting, and a hardened deploy) is in place. The encouraging news is that the foundations are sound and the gaps are specific and fixable; a focused two-to-four-week hardening sprint against the roadmap below can bring this to a defensible launch.

## 2. What the Application Actually Does

ErrandGuy is a two-sided, real-money on-demand errand and delivery marketplace for the Philippines (PHP), connecting customers who need tasks done — deliveries, shopping/pabili, queueing, bills payment, and person transport — with vetted "runners" who fulfill them for pay. It is built as a dual-role Expo/React Native app over a Laravel API with a Filament admin panel, backed by MySQL, Redis, and Reverb for realtime, and Xendit for payments. A customer picks an errand type, enters pickup/dropoff and task details, sees a live price estimate (base fee + vehicle premium + distance + a configurable ~15% platform service fee + any type surcharge, minus promo), and pays by wallet balance, linked e-wallet (GCash/Maya/GrabPay), card, or cash under a client idempotency key; the server dispatches a matching job, and the customer live-tracks the runner on a map with chat, ETA, and a status timeline through to completion and bidirectional rating, with optional tips passing 100% to the runner.

On the runner side, users complete document (KYC) verification, go online and stream location, receive and accept offers (including a "negotiate" pricing path), advance a strict per-errand-type status machine (with photo/receipt proof and a PIN check for rides), and on completion are credited runner_payout (fare minus the service fee) to an earnings balance they later withdraw via admin-approved payout; the platform keeps the service fee. Ops staff verify runners, manage/suspend users, oversee bookings, resolve disputes, configure payment methods and system config, disburse payouts, and respond to SOS/safety events. The money layer is guarded by decimal columns, row-locked transactions, layered idempotency (client key + DB unique index + gateway key + webhook dedup), an audited Payment::transitionTo status funnel, and pull-based reconciliation as a webhook fallback. Notably, a parallel NestJS backend reimplements the same money logic against the same database (only Laravel is deployed to production), a documented drift/audit risk.

## 4. Top Launch-Blocking Risks

**From Sweep 1:**

1. Runner KYC documents (government IDs, selfies, licenses) are stored on a world-readable public disk with guessable timestamp filenames keyed only by a runner UUID that any past customer already knows, an unauthenticated identity-document breach (SEC-1).
2. There is no database backup, point-in-time recovery, or DR plan for the wallet/payment/payout data, so a corrupt migration, disk failure, or bad admin action causes irreversible financial data loss (DEVOPS-2).
3. Production runs APP_DEBUG=true, leaking stack traces, file paths, and internals via the Filament admin panel and meta.debug on every 5xx API response, materially easing exploitation of a payments system (DEVOPS-1 / SEC-2).
4. Real money is lost or mislocated at the completion/settlement seam: runners are never credited when a charge settles after completion (MONEY-1), cash+promo bookings shortchange the runner by the promo amount (MONEY-2), and cancelling a booking with an in-flight charge takes the customer's money with no auto-refund (MONEY-3).
5. Retry-match revives an auto-cancelled-and-already-refunded booking without re-charging, letting a customer get a free errand while the fulfilling runner is paid nothing (BOOK-1).
6. The money-moving admin panel has no 2FA and lets an operator type an arbitrary free-text payout destination, so a single phished or rogue admin can drain any runner's balance to their own account (ADMIN-1, ADMIN-2).
7. The entire booking-recovery and money-unlock safety net (auto-cancel, stale-match rescue, ride-safety monitor) is queue/scheduler-dependent with no worker-health or dead-letter alerting, so a worker outage silently freezes customer refunds and safety monitoring (DEVOPS-3 / SCALE-REL-1).
8. Production is observability-blind and the flagship live experience is misconfigured: no backend error tracking or mobile crash reporting and only a trivial /up health check (DEVOPS-4/6), while the production EAS build ships a placeholder Reverb key and wrong API host and realtime defaults to off (DEVOPS-8 / SCALE-REL-2).

**New blockers surfaced by Sweep 2:**

1. MONEYX-1 (HIGH, confirmed): a payout reversal arriving after a successful disbursement silently drops the runner re-credit, so the runner is permanently debited for money that never reached them, with no reconciler backstop.
2. PRIV-1 (HIGH, confirmed): account deletion does not honor erasure — gov-ID images, bank/payout details, addresses and third-party contacts are retained indefinitely and, combined with SEC-1, deleted runners' gov IDs stay publicly reachable forever, a DPA blocker that compounds an existing critical.
3. RT-1 (HIGH, confirmed): the stale legacy fcm_token fallback pushes one user's notifications and PII to whoever last logged in on a shared device after an account switch.
4. PRIV-2 + PRIV-3: consent is never persisted server-side and the privacy notice is self-labeled placeholder copy omitting real processors — the platform cannot demonstrate DPA-compliant consent, a pre-launch legal blocker for a PH money marketplace.
5. OTP/SMS is entirely unwired (confirmed): while it degrades gracefully and blocks no login path, phone numbers are never verified in production and there is no SMS channel at all — a trust/ops gap that also has no spend cap once wired.

### Money-safety & payment business logic — `MONEY` · Sweep 1 · score 73/100

> The wallet/payment core is the strongest part of the system: decimal money columns, lockForUpdate on every mutation, layered idempotency (client key + the uq_wallet_tx unique index + gateway keys + webhook dedup), an audited Payment::transitionTo funnel, and settled-in-full checks, with the historic P0s (double-refund, payout double-debit, referral farming, cash-completion leak) verifiably closed. But three real money-loss defects survive in the completion/settlement seam: a runner is never paid when a gateway charge settles after completion (MONEY-1), cash+promo bookings shortchange the runner by the promo amount and overstate earnings (MONEY-2), and cancelling a booking with an in-flight charge takes the customer's money with no auto-refund (MONEY-3). There is also no automated ledger-vs-balance reconciliation (MONEY-6), which is doubly risky given the second NestJS engine writing the same database. MONEY-1..3 are launch blockers; the rest is pre/post-launch hardening.

The payment and wallet layer is, on the whole, one of the strongest parts of this codebase and shows clear evidence of a prior money-safety hardening pass that largely held: money columns are DECIMAL (not float) with 2dp casts (Payment/Booking/WalletTransaction models); every wallet mutation runs inside DB::transaction with User row lockForUpdate; a durable idempotency middleware plus a DB-level partial unique index uq_wallet_tx_user_reference_type backstop double-refund/double-earning/double-charge; the Xendit webhook verifies x-callback-token with hash_equals and dedups via WebhookEvent; Payment status moves only through the audited transitionTo funnel with a strict transition table; under-settlement is refused on both webhook and pull-reconcile paths (settledInFull); promo redemption TOCTOU is closed with a conditional UPDATE + consumption-verified unredeem on every terminal path; referral rewards are non-withdrawable (bonus_balance) with self-referral, per-referrer cap, and qualifying-non-cash-booking gates; payout is debited at request time and only re-credited by an atomic failPayout; and the historic cash-completion leak is fixed (cash credits nothing to the runner wallet, only a commission debit). I verified the previously-flagged P0s (double-refund, payout double-debit, withdrawable-referral farming, payment_status drift, cash-pays-uncollected-money) are addressed in current code.\n\nHowever, three genuine money defects remain that can lose or mislocate real money, all in the completion/settlement seam rather than the well-guarded core: (1) HIGH — a runner is never credited their earning if a gateway charge settles AFTER the errand is completed (webhook lag / dropped webhook), because earning-crediting lives only in handleCompletion which runs once at completion and the later webhook/reconcile only flip payment_status; there is no earnings backfill (a referral backfill exists, proving the window is known). (2) HIGH — cash + promo bookings silently shortchange the runner: the cash commission is the full service_fee and ignores promo_discount, so the promo cost is taken out of the runner's collected cash instead of the platform, and total_earnings is overstated. (3) HIGH — cancelling a booking while its e-wallet charge is still in-flight charges the customer with no automatic refund (cancel refunds only when payment_status is already 'paid', does not void the charge, and the later webhook marks a cancelled booking 'paid'). Plus a MEDIUM tip double-charge race resolved only by a manual-refund CRITICAL log, non-atomic booking-create promo leak on process death, and the absence of any automated ledger-vs-balance reconciliation (notably risky given the documented second NestJS backend on the same DB). Fixing MONEY-1..3 should be a launch blocker; the rest are pre/post-launch hardening.

### Booking lifecycle, matching & runner assignment — `BOOK` · Sweep 1 · score 68/100

> The booking state machine's concurrency handling is production-grade — every lifecycle mutation re-reads FOR UPDATE and re-checks status inside the transaction, matching additionally locks the runner row, and many prior-audit bugs are verifiably fixed. The gaps are in money-lifecycle completeness beyond the happy path: retry-match revives an already-refunded booking without re-charging (free errand, unpaid runner — BOOK-1), a runner who accepts then abandons strands the booking with the customer forced to pay a fee to escape (BOOK-2), and pabili goods cost is captured but never settled so runners front item money uncompensated (BOOK-3). Secondary defects: the ride PIN is never enforced as a state gate (BOOK-4), and acceptance_rate — which feeds matching order — is computed from the wrong denominator, only decreases, and is self-manipulable (BOOK-5). The concurrency foundation is solid; the lifecycle-money edges are not.

The core booking state machine and its concurrency handling are genuinely strong: every lifecycle mutation (match, accept, status advance, cancel, auto-cancel, negotiate-expire, stale-match sweep) re-reads its row FOR UPDATE and re-checks status inside the transaction, matching (MatchRunnerJob) additionally locks the runner's User row to prevent two bookings claiming the same runner under READ COMMITTED, and settlement is idempotent (WalletTransaction uniqueness + earning/commission existence check). Many issues flagged in the prior SYSTEM_AUDIT are verifiably fixed in current code — CheckRideDurationJob and ExpireStaleMatchesJob are now actually scheduled (routes/console.php), the negotiate offer is really charged (PricingService::applyNegotiateOffer), the cash-completion leak is closed via a negative-commission debit, and the double-fee payout bug is gone. Per-errand-type transition flows (standard/transport/single-location) are strictly sequential with no skips or reversals. However, the workflow has real gaps beyond the happy path: (1) reviving an auto-cancelled + already-refunded booking via retry-match re-opens it without re-charging, yielding a free errand and an unpaid runner; (2) there is no recovery path for a runner who accepts then abandons — the booking strands indefinitely holding prepaid funds and the customer must pay a fee to escape the runner's no-show; (3) shopping/pabili goods cost is captured but never settled, so runners front item money uncompensated on wallet/online bookings; (4) the ride PIN safety check is never enforced as a state gate; and (5) acceptance_rate, which feeds matching order, is computed from the wrong denominator, only ever decreases, and is spammable. The concurrency foundation is production-grade; the money/lifecycle-completeness edges are not yet.

### Money-safety & payment business logic (`MONEY`) · Sweep 1

#### 🟠 High · MONEY-1 — Runner earning is never credited when a gateway charge settles AFTER the errand is completed `✓ verified`

- **Category:** correctness
- **Location:** `app/Http/Controllers/Runner/RunnerErrandController.php:636-665 (handleCompletion); app/Http/Controllers/Payment/XenditWebhookController.php:321-328 (handlePaymentSucceeded); app/Services/PaymentService.php:698-704 (reconcileBookingPayment)`
- **Evidence:** handleCompletion() credits the runner an 'earning' WalletTransaction only inside the `if ($booking->payment_status === 'paid')` branch, and it is the ONLY place an 'earning' row is ever created (grep confirms: earning is written only at RunnerErrandController.php:640). It runs exactly once, synchronously, when the runner marks the errand completed (called only from updateStatus:458). When a GCash/Maya/card charge is still in flight at completion time (payment_status='pending'/'processing' — webhook lag, dropped webhook, or customer app backgrounded so the pull-reconciler never fires), handleCompletion falls through to the `else: credit nothing` branch and never marks the payment collected. When the payment.succeeded webhook (or reconcileBookingPayment) later settles, it only does `booking->update(['payment_status' => 'paid'])` and rewards the referral — it does NOT create the runner 'earning' row and does NOT re-invoke handleCompletion. A dedicated referral re-attempt (rewardReferralIfEligible) was added for exactly this lag window, but no equivalent exists for runner earnings.
- **Impact:** The platform collects the customer's money (payment settles) but the runner's payout is permanently lost — their wallet is never credited runner_payout and total_earnings is understated. Silent, automatic runner underpayment with no reconciliation backstop; only a manual admin wallet adjustment recovers it.
- **Root cause:** Settlement (webhook/reconcile) and runner-earning crediting are coupled only through handleCompletion, which runs once at completion time and assumes payment is already settled.
- **Recommended fix:** On late settlement, settle the runner too. In handlePaymentSucceeded / reconcileBookingPayment, after flipping payment_status to 'paid', if booking.status is already 'completed' and no 'earning' row exists for (runner_id, booking_id), credit runner_payout via the same locked, idempotent path handleCompletion uses (guarded by the uq_wallet_tx_user_reference_type index so a later normal completion can't double-credit). Extract the 'credit runner earning' logic into WalletService so both completion and settlement call one idempotent method.

#### 🟠 High · MONEY-2 — Cash + promo booking silently shortchanges the runner (promo cost pushed onto the runner instead of the platform) `✓ verified`

- **Category:** correctness
- **Location:** `app/Http/Controllers/Runner/RunnerErrandController.php:649-664 (handleCompletion cash branch); app/Http/Controllers/Customer/BookingController.php:206-210`
- **Evidence:** On a paid (wallet/online) booking the platform absorbs the promo: it collects total_amount (= gross − promo_discount, BookingController:208) and pays the runner the full runner_payout (= gross − service_fee, stored WITHOUT promo at BookingController:210), so platform net = service_fee − promo. On a CASH booking the customer physically hands the runner total_amount = gross − promo_discount, and handleCompletion debits the runner a commission of the FULL service_fee (`$commission = round((float) $booking->service_fee, 2)`, line 651) with no promo offset. Runner's real net = (gross − promo) − service_fee = runner_payout − promo, i.e. the runner is short by the entire promo_discount. Meanwhile earnedForStats is set to the un-discounted payoutAmount (line 662), overstating total_earnings. Promos are not restricted to non-cash methods (PromoService::validate has no method gate; BookingController applies the promo before the payment-method branch).
- **Impact:** Every cash booking that used a promo underpays the runner by exactly the promo discount and simultaneously inflates the runner's reported total_earnings — a real, recurring money-fairness defect and a ledger inconsistency (stat vs actual net diverge).
- **Root cause:** The cash commission is computed from service_fee alone and ignores booking.promo_discount, which the platform (not the runner) is supposed to fund.
- **Recommended fix:** On the cash path, net the promo out of the commission so the platform absorbs it exactly as on the paid path: `$commission = round((float)$booking->service_fee - (float)$booking->promo_discount, 2);` (allowing a negative commission = a net credit when promo > service_fee), and set earnedForStats to the runner's true net. Add a regression test for cash+promo runner net = gross − service_fee.

#### 🟠 High · MONEY-3 — Cancelling a booking whose gateway charge is still in-flight charges the customer with no automatic refund `✓ verified`

- **Category:** correctness
- **Location:** `app/Http/Controllers/Customer/BookingController.php:641-663 (cancel); app/Http/Controllers/Payment/XenditWebhookController.php:301-330 (handlePaymentSucceeded)`
- **Evidence:** cancel() refunds only when `$locked->payment_status === 'paid'` at cancel time (line 641). For a GCash/Maya/card booking, payment_status is 'pending' (BookingController:408) or 'processing' until the webhook settles, and CancellationPolicy allows a free cancel while status is pending/matched. cancel() does not void/expire the in-flight Xendit charge (grep confirms no void/cancel call in the cancel path or PaymentService) and does not transition the Payment. A moment later payment.succeeded arrives; handlePaymentSucceeded advances the still-'processing' Payment to Completed (canAdvance=true) and sets `booking->payment_status = 'paid'` (line 327) on the now-cancelled booking, with no refund logic for cancelled bookings. Result: the customer is charged in full for a cancelled errand.
- **Impact:** Customer pays for a booking they cancelled and receives no automatic refund; recovery requires a manual admin refund. Reproducible whenever a customer authorizes an e-wallet charge and cancels before the webhook lands (common on slow webhooks / quick cancels).
- **Root cause:** Refund-on-cancel is gated on payment_status==='paid' at the instant of cancel, ignoring charges that settle immediately afterward, and there is no post-settlement refund path for cancelled bookings.
- **Recommended fix:** When settlement lands on a booking whose status is 'cancelled' (or payment_status is 'refunded'/'failed'), auto-refund to wallet (net of any cancellation fee) via the idempotent WalletService::refund + Payment→Refunded path, OR have cancel() proactively expire/void the in-flight Xendit payment_request. At minimum, block a free cancel while a gateway charge is 'processing', or mark such payments for auto-refund on settlement.

#### 🟡 Medium · MONEY-4 — Wallet-funded tip and a still-pending gateway tip can both collect — resolved only by a post-hoc manual-refund alarm 

- **Category:** correctness
- **Location:** `app/Services/WalletService.php:511-535 (completeGatewayTip duplicate guard); app/Http/Controllers/Customer/BookingController.php:1069 (tipCheckout) & 1019 (tip)`
- **Evidence:** Both tip entry points reject only when `booking.tip_amount > 0` (tip:1019, tipCheckout:1069), but tip_amount is set only when a tip actually settles. A gateway tip creates a 'tip_payment' row and returns a checkout_url without setting tip_amount. A customer can therefore start a gateway tip (charge in flight) and then also call the wallet tip(), which passes its own guard (it checks only for an existing type='tip' row, not the pending 'tip_payment') and credits the runner + sets tip_amount. When the gateway tip later settles, completeGatewayTip detects `alreadyTipped` and, rather than crediting twice, marks the row 'completed' with description 'duplicate — refund required' and logs `Log::critical('...MANUAL REFUND REQUIRED')` (lines 520-535). - **Impact:** Runner is correctly paid once (good), but the customer can be double-charged (wallet tip + gateway tip) and is made whole only by an operator noticing a CRITICAL log and issuing a manual refund. No automatic reversal.
- **Root cause:** The 'one tip per booking' guard keys on tip_amount, which is only set at settlement, leaving a window where a pending gateway tip and a wallet tip both proceed.

#### 🟡 Medium · MONEY-5 — Booking-create money mutation is not a single atomic transaction; a mid-sequence process death can leak a promo use 

- **Category:** correctness
- **Location:** `app/Http/Controllers/Customer/BookingController.php:167-465 (store)`
- **Evidence:** store() performs a sequence of independent writes with no enclosing DB::transaction: Booking::create (167), promo redeem (236, its own tx that increments used_count), Payment::create + WalletService::deduct/gateway calls (263-465). Handled failure paths call failBooking() which unredeems the promo and marks the booking failed. But the promo is redeemed (used_count++) BEFORE the payment step, so if the PHP worker dies (OOM/timeout/deploy) between redeem (236) and the payment branch, the promo use is leaked with no unredeem — the conditional-decrement safety in PromoService::unredeem is never invoked. The gateway idempotency-key is derived from the pre-created payment id, so a client retry mints a NEW booking + NEW promo redeem rather than resuming, compounding the leak.
- **Impact:** Rare but real promo-slot leakage (used_count drifts above true consumption) on abnormal termination between redeem and payment; over time a limited promo can be exhausted by ghost redemptions. Not a direct cash loss but degrades a money-adjacent limit and audit accuracy.
- **Root cause:** Ordering: promo consumption happens before the payment collection step and outside a single atomic unit.
- **Recommended fix:** Redeem the promo AFTER payment is confirmed/initiated (or move the whole booking+payment+redeem sequence into one DB::transaction with the gateway call performed after commit), so a failure before settlement never consumes a slot. Keep the HTTP idempotency key stable across retries for the same attempt so a retry resumes rather than re-creates.

#### 🟡 Medium · MONEY-6 — No automated ledger-reconciliation invariant between users.wallet_balance / bonus_balance and the wallet_transactions ledger 

- **Category:** reliability
- **Location:** `app/Services/WalletService.php (deduct/tip/adjust/payout/refund/completeTopUp all do user->update(['wallet_balance'=>...])); app/Http/Controllers/Runner/RunnerErrandController.php:637-661`
- **Evidence:** Balances are maintained as denormalized columns (users.wallet_balance, users.bonus_balance) mutated by raw ->update across at least seven code paths (deduct:266, tip:320/331, adjust:653, payout:789, refund:738, completeTopUp:170, handleCompletion:646/661, failPayout:875), each also snapshotting balance_after on the ledger row. - **Impact:** If any single path (or the second backend) ever writes a balance without a matching ledger row (or vice-versa), the discrepancy is invisible until a runner/customer disputes. No detective control exists for the highest-value invariant in the system.
- **Root cause:** Balance is a mutable denormalized column with no periodic invariant check against its own append-only ledger, and a second backend shares the table.

#### 🟢 Low · MONEY-7 — Idempotency-Key request fingerprint hashes only json_encode($request->all()), excluding uploaded files and sensitive to serialization order

#### 🟡 Medium · PRICE-1 — Distance fare is priced on straight-line Haversine, not routed road distance — systematic under-pricing and runner under-payment `↕ adjusted`

- **Category:** pricing-correctness
- **Location:** `errandguy-api/app/Services/PricingService.php:56-63, 277-295 (routeDistanceKm/haversineDistance)`
- **Evidence:** routeDistanceKm() (L284-294) computes each leg with haversineDistance() (L253-267), the crow-flies great-circle distance. Real driving distance on a road network is routinely 1.2x-1.6x the straight-line distance (rivers, one-ways, no diagonal roads), and much worse across water/expressway-only corridors common in Metro Manila. The customer is quoted, and the runner is paid, only the straight-line km. There is no routing/Directions API and no detour multiplier to compensate.
- **Impact:** Every distance-based fare is systematically below the real cost of the trip. Because runner_payout = total_amount - service_fee and distance_fee is a payout component, the runner is under-compensated for the extra distance they actually drive/ride on every job — a structural fairness defect that grows with trip length and worsens supply retention. #### 🟠 High · MONEYX-1 — payout.reversed after a payout has already SUCCEEDED silently drops the runner re-credit - runner permanently debited for money that never reached them `✓ verified`

- **Location:** `app/Http/Controllers/Payment/XenditWebhookController.php:76-128 (handlePayoutFailed, guard L116); app/Services/WalletService.php:809-838 (completePayout sets status='completed'), 847-885 (failPayout guards status==='pending')`

#### 🟡 Medium · AUTHX-1 — SMS delivery unwired in prod: phone verification and phone-OTP-login are dead, and there is no phone-based account-recovery path `↕ adjusted`

- **Category:** auth-availability
- **Location:** `errandguy-api/app/Services/OTPService.php:64-74; app/Http/Controllers/Auth/OTPController.php:40-55; app/Http/Controllers/Auth/PasswordResetController.php:19-60; errandguy-mobile/src/app/(auth)/register.tsx:255-261`
- **Evidence:** OTPService::sendViaSMS() unconditionally `throw new \RuntimeException('SMS delivery is not configured.')`. OTPController::sendOTP catches it, drops the just-stored OTP (invalidateOTP), and returns OTP_DELIVERY_FAILED (line 46-54). So every phone `send-otp` fails and phone-OTP-login (verifyOTP mints a bearer token) is unreachable for the SMS channel. Password reset is email-only: ForgotPasswordRequest requires `email` and PasswordResetController::forgotPassword mails a code via Mail::raw — there is no phone/SMS reset route anywhere in routes/api.php:64-65. Registration permits phone-only accounts (RegisterRequest: email is `required_without:phone`), and the mobile register screen funnels any phone-providing signup straight into the OTP screen (register.tsx:257 `authService.sendOTP({ phone })` → verify-otp), which now always errors post-signup.
- **Impact:** phone_verified can never become true in production for anyone (any feature gated on it is permanently unusable), and phone-OTP passwordless login is non-functional. A phone-primary account (allowed by the API contract / any non-app client) that forgets its password has NO recovery channel and is permanently locked out, since reset is email-only and SMS OTP is dead. App users are pushed into a verification step that cannot succeed, degrading every phone signup.
- **Root cause:** No SMS provider (Semaphore/Twilio) integrated; the reset broker was built email-only while registration and the OTP model assume a working phone channel.
- **Recommended fix:** Either wire a real SMS provider before launch, or (a) hard-disable the phone OTP/verification path in the API and mobile flow so users aren't funneled into a dead step, and (b) add an SMS-based password-reset channel OR require email at registration (make email non-optional) so every account has at least one working verification+recovery channel. Track which channel an account can actually be recovered through.

#### 🟡 Medium · AUTHX-2 — Multi-device token identity collapses to User-Agent: password login revokes a user's other sessions; OTP/register accumulate unbounded, never-pruned tokens 

- **Category:** token-lifecycle
- **Location:** `errandguy-api/app/Http/Controllers/Auth/LoginController.php:53-58; app/Http/Controllers/Auth/OTPController.php:110; app/Http/Controllers/Auth/RegisterController.php:60; errandguy-mobile/src/services/auth.service.ts:13-15`
- **Evidence:** Token name is `device_name` defaulting to the User-Agent header: LoginController.php:53 `$deviceName = $request->input('device_name', $request->header('User-Agent', 'mobile'))`. The mobile client never sends device_name (auth.service.ts:13 posts only phone/email/password), so every device shares one effectively-constant name. Login then does `$user->tokens()->where('name', $deviceName)->delete()` (line 56) before minting — deleting ALL of the user's tokens that share that name, i.e. every other logged-in device. The OTP path (OTPController.php:110) and register path (RegisterController.php:60) mint `createToken($request->header('User-Agent','mobile'))` with NO pre-delete and no cap, so those tokens pile up. Sanctum tokens are minted with no abilities → wildcard '*'. There is no `sanctum:prune-expired` scheduled command evident.
- **Impact:** Genuine multi-device use is broken for password login: signing in on phone B silently logs the user out of phone A. Meanwhile every register/OTP verify leaves a live wildcard-ability token behind forever (30-day TTL, config/sanctum.php:52) with no rotation and no server-side pruning, so a single user can accumulate dozens of long-lived fully-privileged tokens — a larger theft surface and no way for the user to see or revoke them.
- **Root cause:** Device identity is derived from a non-unique User-Agent instead of a stable per-install device id, and only the login path does same-name revocation while OTP/register do not.
- **Recommended fix:** Send a stable per-install device identifier from the client and use it as the token name; scope revocation to that device id. Give tokens least-privilege abilities per role instead of wildcard. Schedule `sanctum:prune-expired`. Add a 'sign out this/other devices' surface backed by per-token revoke.

#### 🟡 Medium · AUTHX-3 — Pre-auth account-lockout DoS: login rate-limit keyed solely on the victim's identifier 

- **Category:** brute-force-dos
- **Location:** `errandguy-api/app/Http/Requests/Auth/LoginRequest.php:26-47; app/Http/Controllers/Auth/LoginController.php:24,38; errandguy-api/bootstrap/app.php:86-101`
- **Evidence:** LoginRequest::ensureIsNotRateLimited/incrementAttempts key the counter purely on the target identifier: `'login_attempts:' . ($this->input('phone') ?? $this->input('email'))` (lines 28,43), locking that account for 15 minutes after 5 failures (line 31, 45-46) regardless of source IP. The route-level throttle:auth adds a per-identifier bucket too (`Limit::perMinutes(15,5)->by('auth:'.$identifier)`, bootstrap/app.php:98). An attacker never needs the victim's password: 5 junk POSTs to /auth/login with the victim's email trip the lockout, and the message even confirms the account exists ('Too many login attempts...').
- **Impact:** Any unauthenticated attacker can deny login to any user whose email/phone they know (enumerable per the already-logged SEC-3 oracle) for rolling 15-minute windows indefinitely, and the lockout message doubles as an existence confirmation. Cheap, targeted account-availability DoS against runners mid-shift or customers mid-booking.
- **Root cause:** Lockout is modeled as per-credential only, with no IP/device dimension and no distinction between attacker-driven and victim-driven failures.
- **Recommended fix:** Key throttling on a composite of identifier AND source IP/device (or apply the hard per-identifier lock only after correlating repeated distinct-IP failures), use exponential backoff rather than a flat 15-min freeze, and return a neutral lockout message that does not confirm account existence.

#### 🟢 Low · AUTHX-4 — Client-side-only logout leaves tokens valid server-side; no server revoke on 401/403 recovery or remember-me cold-start 

- **Category:** token-revocation
- **Location:** `errandguy-mobile/src/services/api.ts:293-313; errandguy-mobile/src/stores/authStore.ts:206-227,229-250; errandguy-api/app/Http/Controllers/Auth/LogoutController.php:11-18`
- **Evidence:** Server logout revokes only the current token (LogoutController.php:13 `currentAccessToken()->delete()`), and only the explicit user-initiated logout (useAuth.logout → authService.logout) calls it. Other 'sign-out' paths clear state locally without any server revoke: the api.ts 401 interceptor just `secureStorage.remove('auth_token')` + resets the store (api.ts:294-306); the authStore.logout action used by _layout.tsx's 401/403 recovery (authStore.ts:144, 210-213) and the remember-me cold-start (`session_persistent === 'false'` → removes local token, authStore.ts:246-249) never hit /auth/logout. There is no 'revoke all sessions' capability and no revocation when an admin suspends a user (EnsureUserActive only blocks at request time; the token stays live).
- **Impact:** Tokens dropped by any local-only path remain valid on the server for the full 30-day TTL. A token captured before such a 'logout' (e.g. from a keychain/backup extraction, or a 403-suspended session) is still usable directly against the API until it expires or the user happens to do an explicit logout or password reset. Suspension is enforced only while the `active` middleware runs, so it does not truly kill the credential.
- **Root cause:** Logout/expiry is treated as a client-state operation; server-side revocation is wired to only one of several sign-out paths, and status changes don't invalidate tokens.
- **Recommended fix:** Make the 401/403 handler and the remember-me cold-start best-effort call /auth/logout before clearing local state; add an authenticated 'revoke all my tokens' endpoint; and revoke a user's tokens server-side when an admin suspends/bans/deletes the account instead of relying solely on per-request status checks.
